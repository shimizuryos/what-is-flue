## 会話は「ID」で管理される

Flue のエージェントは、必ず **ID** 付きで呼び出されます。ID の意味は自由です。ユーザーID、問い合わせチケット番号、GitHub の Issue 番号など、アプリに合わせて決めます。

- **同じ ID** にメッセージを送る → 前の会話の続きになる（履歴を覚えている）
- **違う ID** にメッセージを送る → まっさらな新しい会話になる

会話は自動で保存されます。`flue run` の場合はプロジェクトのデータベース（未設定ならローカルの SQLite ファイル）に保存されるので、**プロセスが終わっても続きから話せます**。このアプリもワークスペースごとの SQLite に保存しています。

```bash
npx flue run src/agents/memo.ts --id memo-1 --message "私の好きな果物はりんごです"
npx flue run src/agents/memo.ts --id memo-1 --message "私の好きな果物は何でしたか？"
```

関数の引数 `{ id }` で、エージェントのコードからも ID を読めます。

## 試してみよう：会話が続くこと

1. 「私の好きな果物はりんごです」を送る
2. 続けて「私の好きな果物は何でしたか？」を送る
3. 🔍 **モデルへの入力** を開き、1 回目のやりとりが **履歴（messages）としてモデルに送られている** ことを確認する

モックLLMは文章を理解しませんが、「この会話の履歴: これまでに N 件のメッセージを覚えています」と返します。本物の LLM なら「りんごです」と答えるはずです。

次に、上部の **会話ID** を `memo-2` に変えて同じ質問をしてみましょう。履歴がリセットされ、「これが最初のメッセージです」になります。（**＋ 新しい会話** ボタンでもランダムな ID に切り替えられます）

## エージェント関数は毎ターン「再レンダー」される

React のコンポーネントが state の変化で再描画されるように、Flue のエージェント関数は **モデルを呼ぶ直前に毎回** 実行されます。

ログ欄の `[render]` の行に注目してください。ツールを使うレッスン（次のレッスン）では、1 回のメッセージで複数回モデルが呼ばれ、そのたびに関数が実行されるのが分かります。

このおかげで、エージェントへの指示や使えるツールを「その時点の状態」から毎回組み立て直せます。これが Flue の「**Dynamic（動的）**」という設計思想です。

> ⚠️ 指示に `Date.now()` のような毎回変わる値を入れると、LLM のプロンプトキャッシュが効かなくなりコストが上がります。本番では注意しましょう。

## やってみよう

1. 会話ID を変えたり戻したりして、履歴がどう変わるか確かめる
2. `return` の中で `id` を使って、ID ごとに違う性格のアシスタントにしてみる（例: `id.startsWith('cat')` なら猫語）
